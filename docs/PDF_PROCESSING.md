# PDF 처리 상태와 OCR 후보 판별 (#30), OCR (#31)

## 실행 및 복구

업로드는 PDF 검증과 페이지 수 확인을 동기적으로 수행한다. 원본 파일을 저장한 뒤 Document와 `pending` 작업을 같은 SQLite 트랜잭션에 기록한다. 업로드 응답은 기존 Document 메타데이터를 반환한다. `init_db`는 `document_processing` 테이블을 추가하고 작업 행이 없는 기존 자료를 `pending`으로 등록한다. 재실행 시 이미 등록된 작업의 상태와 결과를 유지한다.

로컬 배포는 SQLite DB 하나당 Uvicorn 프로세스 하나를 사용한다. 앱의 lifespan에서 관리하는 작업 스레드 하나가 약 0.5초 간격으로 대기 작업을 찾고, 발견한 작업을 문서 ID 순으로 한 건씩 처리한다. 상태 조회와 재시도 계약은 [API.md](API.md#처리-상태와-재시도-30)를 참고한다.

| 전이 | 동작 |
| --- | --- |
| `pending` → `processing` | 작업 스레드가 현재 상태를 조건으로 갱신하고 커밋한 뒤 원본을 읽는다. 재시도와 작업 획득은 SQLite에서 조건부로 갱신한다. |
| `processing` → `completed` | 모든 페이지를 읽고 `image` 페이지를 OCR한 뒤 `Page` 저장·정리, OCR 결과 저장, 누락된 `page_count` 보정, 페이지 유형과 완료 상태를 한 트랜잭션으로 커밋한다. |
| `processing` → `failed` | 파일 읽기·페이지 추출·OCR·결과 저장에 실패하거나 시작 시 중단됐던 작업을 발견하면 실패 코드를 기록한다. |
| `failed` → `pending` | 사용자 재시도 요청으로 이전 오류를 지우고, 같은 Document의 원본 전체를 처음부터 처리한다. |

- 원본의 경로를 확인하고 바이트를 메모리에 읽는 동안 삭제와 공유하는 파일 잠금을 사용한다. 삭제가 롤백되면 파일 복원이 끝난 뒤 읽는다. PDF 파싱은 원본 파일을 닫고 파일 잠금을 해제한 뒤 수행한다. 결과를 저장할 때는 SQLite 쓰기 잠금으로 삭제와 직렬화하고 Document ID와 서버 저장 파일명을 함께 확인한다. 문서가 삭제되면 관련 작업 행은 같은 트랜잭션에서 SQLite FK cascade로 삭제된다.
- 어떤 페이지든 추출에 실패하거나 저장에 실패하면 이번 실행 결과를 모두 폐기한다. 재실행 시 기존 범위 내 `Page.id`와 이미 저장된 공백 이외의 텍스트를 유지한다. 실제 범위를 벗어난 행은 성공 시 정리한다. 원본과 메모는 처리 단계에서 수정하지 않는다.
- 정상 종료는 진행 중인 한 건을 정리한 뒤 종료한다. 강제 종료 후에는 다음 앱 시작에서 `processing`을 `failed`(`interrupted`)로 바꾼다. 커밋된 `pending`은 자동으로 이어서 처리하고, `failed` 작업은 사용자 요청으로 재시도한다. 동일 DB에 여러 서버 인스턴스를 동시에 시작하는 배포는 지원 범위 밖이다.

## 페이지 종류

`page_kinds`는 PDF의 물리 페이지 순서대로 저장한다. 첫 항목이 1쪽이며 유형은 pypdf가 추출한 원문 텍스트와 PDF 콘텐츠 스트림을 기준으로 정한다. [pypdf의 페이지 콘텐츠 처리](https://pypdf.readthedocs.io/en/stable/_modules/pypdf/_page.html)

| 값 | 판별 기준과 후속 처리 |
| --- | --- |
| `text` | 정규화 후 텍스트가 있고 이미지 그리기 명령이나 확인 불가 XObject가 없다. |
| `image` | 텍스트 없이 이미지 XObject를 호출하거나 인라인 이미지를 그린다. OCR 후보로 사용한다. |
| `blank` | 텍스트·이미지·기타 표시 단서가 없거나 공백만 있다. `/Annots`가 비어 있으면 직접 배열과 간접 참조 배열 모두 주석이 없는 것으로 판단한다. |
| `mixed` | 추출된 텍스트와 이미지가 한 페이지에 있다. 이미지 속 추가 텍스트나 기존 숨은 OCR 텍스트가 있을 수 있어 검토 대상으로 둔다. |
| `unknown` | 이미지로 확인할 수 없는 Form·XObject를 호출하거나, 추출된 텍스트와 이미지 없이 벡터 그리기·주석·추출되지 않은 글자 등 표시 단서가 있다. 검토 대상으로 둔다. |

콘텐츠 스트림에서 호출되지 않은 이미지 리소스는 무시한다. 실제 화면을 렌더링하거나 픽셀을 디코딩하지 않으므로 이미지 면적·클리핑·가시성·Form 내부 이미지·텍스트 품질은 확인하지 않는다. 작은 장식 이미지도 `image`가 될 수 있고, 폰트·벡터로 그린 글자는 `unknown`으로 분류될 수 있다. `completed`는 텍스트 추출과 후보 판별, `image` 페이지 OCR이 끝났음을 뜻한다.

## OCR (#31)

`backend/app/services/ocr.py`가 `image` 페이지만 OCR한다. `text`·`mixed`·`unknown`·`blank` 페이지는 OCR하지 않고 기존 추출 결과를 그대로 둔다.

| 단계 | 동작 |
| --- | --- |
| 실행 위치 | 작업 스레드가 원본을 메모리에 읽고 파일 잠금을 해제한 뒤, DB 트랜잭션 밖에서 실행한다. OCR 중에도 업로드·조회·삭제는 막히지 않으며, 그 사이 삭제된 자료의 결과는 기존 규칙대로 저장하지 않는다. |
| 렌더링 | `pypdfium2`로 페이지를 300 DPI 회색조 이미지로 렌더링하고 `Pillow`로 PNG로 만든다. A4 한 장은 약 2480×3508 픽셀(약 9MB 메모리)이다. |
| 인식 | `tesseract stdin stdout -l <언어>`를 `subprocess`로 페이지마다 실행한다. 언어는 환경변수 `OCR_LANGUAGES`(기본 `kor+eng`), 페이지당 제한 시간은 120초다. 레이아웃 판별은 Tesseract 기본값(`--psm 3`)을 쓴다. |
| 저장 | 결과는 `Page.ocr_text`에 저장하고 `Page.text`(pypdf 추출 결과)는 바꾸지 않는다. 끝의 폼 피드를 지우고 공백만 있으면 `""`로 저장한다. `NULL`은 OCR하지 않은 페이지, `""`는 OCR했지만 글자를 찾지 못한 페이지다. |

| 실패 | `error_code` | 처리 |
| --- | --- | --- |
| `tesseract`가 `PATH`에 없거나 `OCR_LANGUAGES`의 언어 데이터가 설치되지 않음 | `ocr_unavailable` | `image` 페이지가 있는 자료만 실패한다. 텍스트만 있는 자료는 OCR 없이 완료된다. |
| 렌더링 실패, `tesseract` 비정상 종료, 페이지 제한 시간 초과 | `ocr_failed` | 서버 로그에 원인을 남긴다. |

- OCR이 실패하면 #30의 실패 규칙대로 이번 실행의 텍스트 추출 결과도 저장하지 않고, 이미 저장된 페이지·다른 자료·메모는 바꾸지 않는다. 원인을 해결한 뒤 재시도하면 원본 전체를 처음부터 다시 처리한다.
- 한 자료의 OCR은 페이지 순서대로 한 장씩, 작업 스레드 하나에서 실행한다. 스캔 페이지가 많은 자료는 그동안 다음 자료가 `pending`으로 기다린다. 이 환경(Tesseract 5.3.4)에서 300 DPI 한 페이지는 약 0.5초가 걸렸다.
- 한계: 글자가 적고 여백이 넓은 페이지는 자동 레이아웃 판별이 줄 방향을 잘못 판단해 일부 줄이 깨질 수 있다. 직접 만든 한국어 샘플에서 기본값(`--psm 3`)으로 한 줄이 깨졌고, `--psm 4`·`--psm 6`에서는 정상 인식했다. 다단 강의자료를 고려해 기본값을 유지했다. 손글씨, 저해상도 스캔, 기울어진 페이지의 정확도는 확인하지 않았다. OCR 결과의 검색 색인은 #32에서 다룬다.
