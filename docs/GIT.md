# GitHub 협업 규칙

## 1. Branch 전략

### `main`

* 개발 내용을 통합하는 기본 브랜치이다.
* 직접 push하지 않는다.
* 모든 기능 개발 및 수정은 별도 branch에서 진행한 뒤 Pull Request를 통해 `main`에 병합한다.

### 작업 Branch

모든 작업 branch는 최신 `main`에서 생성한다.

형식:

`타입/이슈번호-간단한-설명`

예시:

* `feat/012-login`
* `fix/018-empty-title`
* `refactor/025-api-client`
* `docs/031-readme`

사용하는 타입:

* `feat`: 새로운 기능
* `fix`: 버그 수정
* `refactor`: 기능 변화 없는 코드 구조 개선
* `docs`: 문서 변경
* `test`: 테스트 관련
* `chore`: 설정 및 기타 작업
* `design`: UI/디자인 변경이 많은 경우 사용

하나의 branch에서는 가능하면 하나의 Issue만 처리한다.

---

## 2. Issue 규칙

코드를 작성하기 전에 먼저 Issue를 생성한다.

Issue에는 최소한 다음 내용을 작성한다.

### 작업 내용

무엇을 구현하거나 수정하는지 작성한다.

### 완료 조건

* [ ] 구현해야 할 조건 1
* [ ] 구현해야 할 조건 2
* [ ] 필요한 테스트 또는 확인

### 담당자

작업할 사람을 Assignee로 지정한다.

작업 규모가 지나치게 크다면 하나의 Issue에 모두 넣지 않고 여러 Issue로 분리한다.

---

## 3. Commit 규칙

기본 형식:

`타입: 작업 내용`

예시:

`feat: 로그인 화면 구현`

`fix: 빈 제목 저장 오류 수정`

`refactor: 사용자 조회 로직 분리`

주요 타입:

* `feat` - 기능 추가
* `fix` - 버그 수정 등
* `refactor` - 코드의 논리적 흐름은 유지되는 변경
* `docs` - 문서 변경
* `test` - 테스트 코드 변경
* `design` - UI/UX 변경
* `build` - 빌드 시스템 관련 변경
* `chore` - 그 외 변경 사항

커밋은 가능한 한 하나의 의미 있는 변경 단위로 작성한다.

각 커밋에는 바뀐 내용을 알아볼 수 있는 제목을 적는다.

작업 중에는 진행 상황을 기록하기 위해 여러 커밋을 만들 수 있다.
작업 과정과 각 팀원의 기여가 보이도록 의미 있는 커밋 기록을 유지한다.

---

## 4. Pull Request 규칙

작업이 완료되면 작업 branch에서 `main`으로 Pull Request를 생성한다.

PR에는 다음 내용을 작성한다.

### 변경 사항

이번 PR에서 변경한 내용을 간단히 설명한다.

### 관련 Issue

`Closes #이슈번호`

### 테스트

직접 확인한 내용을 작성한다.

### UI 변경

UI 변경이 있는 경우 가능하면 스크린샷 또는 영상을 첨부한다.

PR 작성자는 다음 항목을 확인한다.

* [ ] 로컬에서 실행 또는 빌드가 정상적으로 완료된다.
* [ ] 관련 없는 코드가 함께 변경되지 않았다.
* [ ] 관련 Issue와 연결되어 있다.
* [ ] 필요한 테스트를 수행했다.

---

## 5. PR Review

모든 PR은 최소 1명의 다른 팀원에게 리뷰를 받은 뒤 병합한다.

리뷰 코멘트에는 필요에 따라 다음 태그를 사용한다.

* `[P1]`: 반드시 수정해야 하는 문제
* `[P2]`: 수정을 권장하는 문제
* `[P3]`: 선택적인 의견 또는 제안

`P1`이 남아 있는 PR은 Merge하지 않는다.

리뷰에서 논의가 끝난 Conversation은 수정 사항을 반영하거나 합의한 뒤 Resolve한다.

---

## 6. Merge 규칙

PR은 기본적으로 **Create a merge commit** 방식으로 병합한다.

Create a merge commit을 사용하면 작업 branch에서 만든 commit 기록을 main에 그대로 남기고, PR이 병합된 사실도 기록한다.

병합 후 작업 branch를 삭제해도 main에 들어간 commit 기록은 사라지지 않는다.

병합 후 작업 branch는 삭제한다.

`main`에는 직접 push하거나 force push하지 않는다.

Merge Conflict가 발생하면 기본적으로 해당 PR의 작성자가 해결한다. 해결이 어렵다면 다른 팀원과 함께 처리한다.

---

## 7. AI Agent 사용 규칙

Cursor, ChatGPT, Codex 등의 AI Agent 사용은 일반적인 코드 작성과 동일한 규칙을 적용한다.
모든 기능 개발 및 수정은 별도 branch에서 진행한 뒤 Pull Request를 통해 병합한다.
* AI Agent가 생성한 코드도 반드시 Issue → Branch → PR 과정을 거친다.
* AI Agent가 `main`에 직접 변경을 넣도록 하지 않는다.
* PR 작성자는 AI가 작성한 코드를 이해하고 설명할 수 있어야 한다.
* 생성된 코드를 실행하거나 테스트하지 않은 상태로 Merge하지 않는다.
* API Key, 비밀번호 등 Secret 정보는 AI Agent나 Repository에 포함하지 않는다.

AI가 작성했다는 이유로 리뷰 과정을 생략하지 않는다.

## 8. Github Projects 규칙

프로젝트의 작업 진행 상황은 GitHub Projects에서 관리한다.

기본 상태는 다음 네 가지를 사용한다.

- `Todo`: 아직 시작하지 않은 작업
- `In Progress`: 현재 작업 중인 항목
- `Review`: Pull Request 리뷰 중인 항목
- `Done`: 병합까지 완료된 작업

모든 개발 작업은 Issue를 생성한 뒤 Project에 등록한다.

작업을 시작하면 `In Progress`,
Pull Request를 생성하면 `Review`,
PR이 Merge되면 `Done`으로 변경한다.

## 9. 문서 관리 규칙

프로젝트 문서는 목적에 따라 `README.md`, `docs/`, GitHub Wiki로 구분하여 관리한다.

같은 내용을 여러 위치에 중복해서 작성하지 않으며,
필요한 경우 다른 문서의 링크를 통해 연결한다.

### README.md

Repository를 처음 방문한 사람이 프로젝트를 빠르게 이해하고 실행할 수 있도록
프로젝트의 핵심 정보만 작성한다.

주요 내용:

- 프로젝트 소개 및 목적
- 주요 기능
- 기술 스택
- 실행 방법
- 팀원 및 역할
- 주요 문서 및 Wiki 링크

상세한 설계나 개발 문서는 README에 모두 작성하지 않고
`docs/` 또는 Wiki로 분리한다.

### `docs/`

소스 코드와 함께 버전 관리되어야 하는 기술 문서를 저장한다.

코드 또는 시스템 구조가 변경될 때 함께 수정되어야 하는 문서는
가능하면 `docs/`에서 관리한다.

예시:

- 시스템 Architecture
- API 명세
- WebSocket / 실시간 통신 Protocol
- Database Schema
- 주요 데이터 구조
- 개발 환경 및 빌드 설정
- 중요한 기술적 설계 및 결정 사항

`docs/`의 문서도 코드와 동일하게
Issue → Branch → Pull Request 과정을 통해 수정한다.

문서만 수정하는 경우 `docs/*` branch와 `docs` Commit 타입을 사용할 수 있다.

### GitHub Wiki

팀원들이 개발 과정에서 지속적으로 참고하거나 공유해야 하는
프로젝트 지식을 관리한다.

예시:

- 프로젝트 개발 가이드
- Git / GitHub 사용 방법
- 기능별 설명
- 개발 과정에서 조사한 내용
- 회의에서 결정된 주요 사항
- 자주 발생하는 문제와 해결 방법
- 외부 자료 및 참고 링크

Wiki는 코드와 직접 연결되지 않는 문서나,
개발 과정에서 지속적으로 추가·수정되는 정보를 기록하는 데 사용한다.

간단한 Wiki 수정은 직접 수행할 수 있으며,
프로젝트의 중요한 규칙이나 설계를 변경하는 경우에는
팀원들과 먼저 공유한 뒤 수정한다.

### 문서 위치 선택 기준

문서를 어디에 작성할지 애매한 경우 다음 기준을 따른다.

- 프로젝트를 처음 보는 사람이 알아야 하는 내용 → `README.md`
- 코드 및 시스템 변경과 함께 관리되어야 하는 기술 문서 → `docs/`
- 팀원들이 개발 과정에서 공유하고 지속적으로 참고할 내용 → GitHub Wiki
